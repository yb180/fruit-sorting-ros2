代码设计的坐标链为：相机点 → 相机到末端外参 → 当前末端到基座变换 → 目标取放位姿。
标定脚本明确写有眼在手上、末端法兰安装描述，并调用 `calibrateHandEye` 求相机到末端外参。
因此源码采用 **eye-in-hand** 方案；实际现场安装位置、当前使用的标定结果仍需用户确认。
SDK 的 `getTcpPose()` 参考的是 TCP；脚本的 `gripper/end/flange` 命名需与标定时实际 TCP 设置对应，不能直接假设 TCP 等于法兰。

## 从源码识别的 CAN 格式

来源：`PCAN_ruiyan16_right_linux.py:15–41,84–99,131–166` 及 PCAN 版本的发送函数。

- Linux 代码读取 `RY_CAN_CHANNEL` / `RY_CAN_BITRATE`，默认 `can0` / `1000000`，设置 `USE_CANFD=False`；这些是源码默认值，不是对现场总线状态的检测结果。
- 代码发送标准帧，电机/仲裁 ID 按 `i+1` 取 1–16。
- 动作报文为 7 字节：`0xAA`、位置低/高字节、速度低/高字节、电流字段低/高字节。
- 原代码的清除报文为单字节 `0xA5`；不能据此将其认定为急停或运动取消命令。
- 缺少接收、状态查询与握持反馈，发送成功不等于动作完成或已经抓稳。原始字段单位、范围和电流语义需核对匹配版本的协议。

本次已将报文布局提取为 `fruit_sorting_planning.legacy_can_codec`，并添加离线测试。
模块仅返回不可变的帧数据：无 `python-can`、无总线初始化、无库加载、无发送函数，也没有接入默认 launch。
输入必须显式传入；整数类型、ID 和字段表示范围会校验，非法值不会像原脚本一样被截断后继续编码。
16 位字段的可编码范围不代表设备允许的物理范围；模块不提供现场动作预设、单位转换或驱动支持声明。

## 接入前需要处理的问题

### 1. 运动等待结果没有传播，状态读取失败会伪装成零位姿

`aubo_robot_linux.py:125–127,159–162` 调用 `_wait_motion_complete()` 后不检查其布尔返回，等待超时仍可能返回成功。
等待函数 `170–199` 根据关节位置短时间稳定判定完成，未确认目标误差、控制器执行状态或故障。
`get_current_waypoint()` / `forward_kin()` 在错误时返回全零默认数据（201–218、236–255），上层难以区分读取失败和真实零值。
`forward_kin()` 实际读取当前 TCP，而不是根据传入关节值做正运动学。

迁移时应显式返回状态/异常、核对运动结束与目标误差，并让失败阻止后续抓取。停止与取消需依控制器实际 SDK 实现，不能用空的 `robot_shutdown()` 包装承诺停止。

### 2. 两个任务对姿态格式的处理不一致

Linux 适配器 `forward_kin()` 返回 `pose[3:6]` 三元素姿态。
`demo3_autograsp.py:564–569` 的任务 1 将其按弧度欧拉角处理；任务 2 的 `947–955` 却访问第四个元素并按四元数重排。
这与同批 Linux 适配器不匹配；只有进入任务 2 的掩码分支时才会触发，不能描述为所有路径都已运行失败。
应先统一 SDK 位姿格式和单位，再转为 ROS 的 XYZW 四元数，并用已知样例验证。

### 3. 标定质量分数为占位值，图像和位姿可能错配

`Hand_eye_calibration_optimized.py:119–123` 的重投影误差函数固定返回 `0.0`；`275–291` 仍以此选择“最佳”算法，不能将打印的零误差视为准确度证据。
该脚本通过未排序的 `glob` 收集图像（201），角点失败会删去图像样本，却仅将机械臂位姿截到相同数量（249–260），没有同步筛除对应位姿。
采集脚本 `121–154` 还可能保存图像但未保存有效 TCP 位姿。

需采用包含样本 ID/时间戳/图像路径/有效位姿的配对记录，同步过滤失败样本，检查 PnP 成功标志，并实现实际可验证的误差或闭环一致性评价。
目前没有上传原始标定图像、`pose_vectors_*.npy` 或独立验证样本，无法重新评估标定精度。

### 4. 当前上传模型是两类检测模型，部分路径依赖分割结果

`last1.pt` 静态 checkpoint 元数据记录：Ultralytics `8.3.9`、`task=detect`、`DetectionModel`、训练模型字段 `yolo11n.pt`、类别 `0: dog` 和 `1: bread`。
这些是文件内的记录，不是本次推理验证结果；模型不是已验证的蔬果分类/分割模型。
任务 1 从检测框生成矩形掩码（`demo3_autograsp.py:577–583`），`p_ab_compute.py:1048–1070` 也有检测框回退。
任务 2 在 `938` 要求 `results[0].masks` 非空：普通检测输出不提供分割掩码时，此分支不会生成候选目标。
不能将矩形框回退等同于真实实例分割，也不能用轴对齐框轮廓证明物体真实抓取方向。
`p_ab_compute.py` 的目标还包含 `mature`，但上传模型静态类别中没有它；需确认是否另有权重。

### 5. 有硬件导入副作用，CAN 发送错误被吞掉

Linux 手部模块 `40–41` 在导入时打开 CAN；PCAN 版本 `5–11` 在导入时初始化设备并可能退出解释器。
Linux 发送函数在没有 bus 时直接返回，异常也只打印日志（84–99），上层不能可靠获得失败结果。
`send_clean()` 不提供动作取消或停止确认。新适配层需显式创建/关闭连接，保留失败信息，再依据真实协议设计反馈。
两套手部表也不一致：`demo3_autograsp.py` 引用动作 8/9，Linux 表含这些行，上传 PCAN 版本的表仅含 0–7，不能假设 Windows/Linux 动作预设可以互换。

### 6. 标定版本与环境补偿不能混用，同类多目标处理有局限

`demo3_autograsp.py:119–124` 与 `p_ab_compute.py:137–142` 的相机到末端矩阵不同；用户选定 demo 任务 1 后，以 demo 中的矩阵作为现行源码参考，不将其等同于重新验证通过的外参。
取物位置还依赖硬编码桌面高度、物体高度、经验偏移和投放点；例如 demo 的 `633,647` 替换了计算中的深度/Z 值，不能将其直接描述为通用的深度定位。
demo 任务 1 在 `549` 先过滤类别，后用过滤列表的索引取原始 boxes（575–578）；未知类别与目标混合时可能取错检测框，同类多个对象也会因 `cls.index()` 重复使用第一个索引。
两份主程序又按类别合并候选对象（demo 的 657 等），需改为独立检测/跟踪 ID，才能支持流水线上同类多件。

### 7. 资源关闭与运行环境仍需整理

demo 的 `main()` 声明 `global robot`（1289），却用 `'robot' in locals()` 决定断开（1433），该清理条件不能可靠覆盖其全局 robot；该 finally 也未停止相机 pipeline。
Linux 适配器的 `set_joint_maxvelc()` 只存储值，而 `move_joint()` 使用固定速度参数；`set_tool_power_type()` 和 `robot_shutdown()` 为兼容空实现，不能当作实际设备配置完成。
源码还包含硬编码登录信息、设备地址和工作目录；迁移配置应从本机受控配置读取，不将原认证值写入 ROS 参数示例或公开仓库。
GUI、键盘交互和 `np.int0` 等版本相关用法需从后台节点中分离并锁定兼容依赖。
